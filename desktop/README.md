# Приложение Windows

Нативное приложение **Ambilight by Levurgi4** написано на C++20 и Qt 6
Widgets. Оно захватывает экран, рассчитывает цвета, раскладывает их по
физической ленте и передаёт готовый RGB-кадр на ESP32.

## Путь кадра

1. Пользователь выбирает конкретный DXGI-экран либо автоматический выбор
   основного.
2. Desktop Duplication или Windows Graphics Capture получает новую текстуру
   выбранного монитора в отдельном рабочем потоке. Способ переключается во
   вкладке «Экран». WGC служит альтернативой при зависании DXGI в играх;
   оба используют дальнейший GPU-конвейер и поддерживают игровой режим.
3. D3D11 compute shader выбирает по 32–128 точек на каждую зону периметра и
   сводит их обычным средним, среднеквадратичным или доминирующим цветом. На
   CPU возвращается только компактный RGB-буфер, а не полный кадр 4K.
4. Чёрные полосы стабилизируются во времени, зоны независимо
   интерполируются в число LED каждой стороны.
5. CPU-фильтр максимум для 300 цветов сглаживает переходы и при необходимости
   ограничивает резкий рост общей яркости периметра.
6. Смещение начала и направление обхода преобразуют логический периметр в
   окончательный физический порядок ленты.
7. Нативный COM-транспорт отправляет кадр на ESP32.

### Нагрузка и ограничения конвейера

- DXGI удерживает полученный кадр между тактами и освобождает его непосредственно
  перед следующим `AcquireNextFrame`. Это уменьшает лишнее копирование обновлений
  рабочего стола во время ожидания, согласно
  [рекомендации Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-releaseframe).
  При остановке и ошибках кадр также освобождается.
- Если поиск чёрных полос выключен, приложение копирует только полосы по краям
  текстуры — и в обычном, и в игровом режиме. Например, при 3840×2160 и глубине
  120 px это 1 382 400 вместо 8 294 400 пикселей на кадр. Это уменьшение именно
  нашей операции копирования, а не всей нагрузки захвата или потери FPS игры.
- WGC использует пул из двух кадров и выбирает свежий. На версиях Windows с
  `IGraphicsCaptureSession5` ограничение частоты задаётся также производителю
  кадров, ещё до запуска сессии. На остальных ограничена только обработка
  приложением: внутренний захват Windows может работать чаще.
- Между захватом, UI и транспортом действуют ограниченные очереди с заменой
  старого кадра новым. Неограниченной очереди, увеличивающей задержку, нет.
- Подготовка скрытого экранного предпросмотра и текста диагностики пропускается.
  Видимый предпросмотр обновляется не чаще 20 раз в секунду; обработка цветов
  для ленты сохраняет заданную частоту. При открытии окна/вкладки отображаются
  последние данные даже при неподвижном рабочем столе.
- При изменении размера WGC-кадра старые отступы чёрных полос сбрасываются сразу,
  а не только на очередном такте детектора.

Основное оставшееся место синхронизации — чтение GPU-результата через `Map`.
Обычно оно выполняется один раз на кадр, при проверке чёрных полос — дважды.
Кольцо staging-буферов с неблокирующим чтением могло бы уменьшить ожидание CPU,
но потребует политики пропуска результатов/задержки и проверки под нагрузкой.
Это не устранит саму GPU-работу. Такой конвейер пока не внедрён, чтобы не
добавлять скрытую задержку к подсветке без измерений.

Другой возможный шаг — читать входную текстуру напрямую, если источник и драйвер
разрешают shader-resource view, с копированием как резервным путём. Сейчас
используется предсказуемая собственная текстура. Также обработку LED можно
вынести из UI в отдельный поток: это уменьшит зависимость от занятости интерфейса,
но не снизит стоимость захвата на GPU. Замеры FPS в конкретной игре нужны
отдельно; время обработки рабочего стола не является таким замером.

Ручной интеграционный тест требует активного рабочего стола: он показывает
небольшое анимированное окно, проверяет по 24 кадра в 10 сценариях DXGI/WGC,
смену FPS, игровые настройки, режимы цвета/чёрных полос и stop/start.
Настройки пользователя и COM-порт он не открывает:

```powershell
cmake --build --preset windows-release --target ambilight_capture_backend_smoke
# Добавьте каталог bin используемого Qt в PATH, если его там ещё нет.
& ".\out\build\windows-release\desktop\Release\ambilight_capture_backend_smoke.exe"
```

## Независимое зеркалирование на ТВ (прототип без размытия)

Во вкладке «Зеркалирование» запускается отдельный D3D11 flip-model вывод на
выбранный расширенный дисплей. Он не зависит от включения ленты или наличия
ESP32. `processLedColors=false` отключает вычисление цветов и GPU→CPU readback;
кадр остаётся на GPU. Если Ambilight включён, источник захвата общий, а сроки
обработки LED и вывода зеркала независимы. Например, 60 FPS зеркала не повышают
30 FPS расчёта цветов игрового режима. При зеркалировании нужны копии полного
кадра; оптимизация копирования только краёв применима не ко всем таким кадрам.

Вывод сохраняет пропорции и ориентацию, не обрезает содержимое и не применяет
LED-гамму/яркость/баланс белого к телевизору. Цепочка вывода содержит два буфера,
максимальная очередь предъявления — один кадр. Доступность проверяется без
ожидания GPU: занятый вывод пропускается, последний кадр хранится на GPU для
повторной попытки даже после остановки изменений на исходном экране. Это не
обещание задержки в один кадр: захват, DWM и ТВ добавляют собственные задержки.

Ограничения прототипа: SDR, до 60 FPS зеркала, два неперекрывающихся экрана на
одной видеокарте; отдельный системный курсор не компонуется. Выбор источника в качестве назначения и клонированные выходы
отклоняются. Windows переключается в «Расширить» вручную; приложение не меняет
разрешения или расположение дисплеев. При WM_DISPLAYCHANGE зеркало выключается.
Окно ТВ не забирает фокус и не скрывается вместе с окном настроек. Перед
уничтожением HWND рабочий поток освобождает swap chain. В настройках сохраняются
только предпочтения назначения/FPS, не состояние запуска и не HWND.

Для проверки вывода без второго физического экрана предусмотрен ручной тест:

```powershell
cmake --build --preset windows-release --target ambilight_mirror_presenter_smoke
# Qt bin должен быть доступен через PATH.
& ".\out\build\windows-release\desktop\Release\ambilight_mirror_presenter_smoke.exe"
```

Он показывает маленькое окно с синтетической текстурой, проверяет цвета и чёрные
поля для четырёх поворотов, изменение размера, скрытие и пересоздание swap chain.
Это проверка рендера, не сквозной замер игры/двух дисплеев. Для сравнения на ТВ
нужны одинаковая сцена RDR2, настройки и лимит FPS: сначала Windows «Дублировать»
с Ambilight выключенным, затем зеркало без Ambilight, затем оба режима вместе.
Сравнивайте средний FPS, 1% low, плавность и задержку на телевизоре. Показатель
времени обработки в UI не измеряет задержку до появления света на экране.

## Путь звука

1. Отдельный поток открывает выбранное устройство через WASAPI: loopback
   звуков Windows, микрофон или оба источника.
2. Стерео/многоканальные PCM либо float-пакеты сводятся в моно только в
   оперативной памяти; аудиофайлы не создаются.
3. FFT 1024 с окном Hann и перекрытием 50% формирует 4–64 логарифмические
   частотные зоны.
4. Независимые усиления, порог тишины, чувствительность, загорание и затухание
   превращают спектр в яркости зон.
5. В пружинном режиме каждая зона дополнительно хранит скорость и проходит
   модель затухающей пружины с ограниченным перелётом; плавный режим оставляет
   обычную экспоненциальную огибающую.
6. Зоны раскладываются зеркально от центра снизу либо один раз по периметру,
   после чего общий путь применяет физический `LED 0`, направление и смещение.
7. Готовый кадр проходит через тот же низколатентный COM-транспорт; яркость,
   баланс белого и расчётный лимит тока применяются прошивкой как обычно.

Автосохранение записывает UI-состояние без повторного открытия WASAPI и без
перезапуска уже применённых конфигураций. Отдельная кнопка запуска переключает
режим прямо со звуковой вкладки, индикатор пика работает независимо от ESP32,
а рекомендуемые параметры можно вернуть без сброса устройств и усилений.

Яркость не «запекается» в передаваемые RGB-байты: приложение приглушает только
предпросмотр, а реальное ограничение яркости, тока и поканальная калибровка
баланса белого выполняются ESP32. Общая яркость вынесена на главную вкладку.
Вкладка ленты позволяет включить тестовый
белый, менять R/G/B ползунками и вернуть выбранный режим одной кнопкой.
Там же есть отдельное окно настройки физического расположения: четыре
счётчика ограничивают общую сумму диапазоном 1–300, рядом меняются логическое
положение физического `LED 0` и направление ленты. Стороны временно
окрашиваются в разные цвета либо выбранная сторона заливается белым, а первый
физический LED отмечается белым. Тестовый кадр поддерживается непрерывно до
закрытия окна. Изменения передаются контроллеру сразу. Во время обоих тестов захват экрана
приостанавливается, чтобы не расходовать GPU и не перезаписывать тестовый кадр.

Для Ambilight доступны временные постоянные сглаживания 0, 25, 60 и 120 мс.
Отдельная защита от вспышек ограничивает только резкий рост средней яркости
периметра примерно за 180 мс и не задерживает затемнение. История фильтра
сбрасывается при остановке захвата и смене разрешения, поэтому кадры 21:9 и
16:9 не смешиваются.

## Подключение к ESP32

Вкладка подключения предлагает два режима:

- **ручной** — пользователь один раз выбирает USB-UART `COMx`, после чего
  корректно ответивший Ambilight-контроллер проверяется через SetupAPI;
- **автоматический** — приложение открывает только ранее подтверждённую
  постоянную идентичность из VID/PID, Container ID и уникального USB serial.
  Номер COM служит только подсказкой и может измениться. Произвольные COM-порты
  не зондируются и не получают бинарный `Hello`.

Bluetooth/RFCOMM намеренно запрещён в обоих режимах: зависший сторонний драйвер
не должен блокировать завершение приложения. Если контроллер ещё ни разу не
подключался, Automatic попросит сначала выбрать его USB-UART порт вручную.
USB-UART без достоверного уникального serial — в частности многие CH340 и
клоны с серийником-заглушкой — намеренно остаётся только в ручном режиме:
Container ID такого устройства может зависеть от USB-разъёма и не доказывает,
что перед приложением тот же физический контроллер.
Если производитель прошил нескольким адаптерам одинаковый, но внешне
правдоподобный serial, Windows не даёт программного способа различить их;
для такой партии также следует оставить ручной выбор COM.

Текущая прошивка использует фиксированные `2 000 000 бод, 8 бит данных, без
чётности, 1 стоп-бит` и без аппаратного управления потоком. После открытия
COM-handle приложение отключает DTR и RTS и дальше намеренно их не
импульсирует. Фактическое поведение линий в момент открытия ещё нужно
проверить с конкретным USB-UART адаптером.

После открытия приложение даёт возможному auto-reset ESP32 300 мс на запуск,
затем начинает `Hello → DeviceInfo`. Пока действует общий handshake deadline,
тот же `Hello` повторяется каждые 200 мс на одном открытом handle — повторное
открытие порта не создаёт reset-loop. Затем приложение отправляет конфигурацию
ленты, яркость, резервный режим и активный режим; изменяющие состояние команды
требуют `Ack` и выполняются по одной. При выборе `Off` он получает приоритет
над ещё не отправленными настройками. LED-кадры допускаются только после
рукопожатия и синхронизации управления.

Открытие порта имеет ограниченный deadline и выполняется вне transport thread.
При обрыве, тайм-ауте ACK или исчезновении ответов порт закрывается, после
чего рабочий поток повторяет подключение только к доверенному контроллеру.
Список COM-портов можно обновить вручную из интерфейса.
Компактный индикатор соединения остаётся виден на всех вкладках и по нажатию
открывает настройки подключения.

## Как сохраняется низкая задержка

- захват и COM-ввод-вывод работают в отдельных потоках;
- между захватом и интерфейсом хранится только одна свежая выборка;
- между интерфейсом и транспортом также хранится только один свежий
  LED-кадр;
- новый кадр заменяет ещё не отправленный старый;
- управляющие команды имеют приоритет перед видеопотоком;
- высокочастотные `LedFrame` не ждут ACK;
- при статичном рабочем столе последний кадр периодически отправляется снова
  с новым sequence number, чтобы lease на ESP32 не истёк;
- в ожидании reconnect транспорт использует редкий coarse timer, а не
  пробуждается каждые 2 мс.

## Автономный режим

Перед включением Ambilight приложение программирует резервный режим: `Off`
или выбранный эффект. Если RGB-поток пропадает дольше заданного тайм-аута,
ESP32 сам переходит на этот режим. При отдельном питании контроллера эффект
может продолжать работать после выключения ПК.

Тот же выбранный эффект можно временно запустить кнопкой на главной вкладке,
не отключая USB. Остановка ручной анимации возвращает сохранённый текущий
режим, обычно Ambilight.

Эта настройка пока живёт только в оперативной памяти ESP32. После
перезапуска контроллер начинает с безопасного `Off`, пока приложение не
установит конфигурацию заново.

## Диагностика

Интерфейс показывает состояние соединения, выбранный порт и версию прошивки,
счётчики переданных байтов и кадров, число заменённых кадров, а также
телеметрию ESP32: последние принятый и применённый sequence number, отброшенные
кадры, ошибки CRC и фактический флаг активного физического выхода.

## Граница текущей проверки

Без контроллера проверены сборка, кодирование пакетов, разбор ответов,
валидация параметров и политика ограниченной очереди. Захват, настройки,
раскладка и общий протокол также покрыты автоматическими тестами.

Реальный COM-порт на 2 Мбит/с, физический handshake, переподключение после
отсоединения кабеля и непрерывная передача на ESP32 должны быть проверены на
устройстве. Наличие готового транспортного кода не означает, что сквозной
аппаратный тракт уже подтверждён.

## Сборка

Из Developer PowerShell для Visual Studio:

```powershell
cmake --preset windows-debug
cmake --build --preset windows-debug
ctest --preset windows-debug
```

Release-сборка:

```powershell
cmake --preset windows-release
cmake --build --preset windows-release
ctest --preset windows-release
```

Запускаемый комплект с Qt runtime:

```powershell
$installDir = Join-Path (Get-Location) "out\install\windows-release"
cmake --install out/build/windows-release --config Release --prefix $installDir
& "$installDir\bin\Ambilight by Levurgi4.exe"
```

Для `--prefix` используется абсолютный путь: Qt deployment отклоняет
относительный. Имя исполняемого файла — `Ambilight by Levurgi4.exe`.
