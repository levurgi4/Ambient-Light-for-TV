# Протокол USB-UART v2

Протокол бинарный, little-endian и передаётся через обычный последовательный
порт. Текущие desktop и firmware используют фиксированные
`2 000 000 бод, 8-N-1`, без аппаратного управления потоком.

На Windows после открытия COM-handle линии DTR и RTS переводятся в
отключённое состояние и затем намеренно не импульсируются. Поведение самих
линий в момент открытия зависит от драйвера USB-UART и проверяется на
конкретной плате. На прошивке каналом протокола служит UART0; вывод логов
отключён, чтобы текст не смешивался с бинарными пакетами.

Максимальный RGB-кадр на 300 светодиодов занимает не более 929 байт на
проводе — примерно 4,65 мс при 2 Мбит/с и 8-N-1.

## Пакет

Декодированный пакет имеет следующий вид:

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 4 | Magic `41 4C 42 31` (`ALB1`) |
| 4 | 1 | Версия протокола (`2`) |
| 5 | 1 | Тип сообщения |
| 6 | 2 | Флаги |
| 8 | 4 | Sequence number |
| 12 | 2 | Размер payload, максимум 1024 |
| 14 | 2 | Reserved, должен быть нулём |
| 16 | N | Payload |
| 16+N | 4 | CRC-32C |

CRC-32C покрывает весь декодированный заголовок и payload. Используются
отражённый полином `0x82F63B78`, начальное значение `0xFFFFFFFF` и финальный
XOR `0xFFFFFFFF`. Эталон для ASCII `123456789` — `0xE3069283`.

Полный декодированный пакет кодируется COBS и завершается байтом `00`.
Благодаря этому нули могут встречаться в RGB-данных, а повреждённый или
оборванный пакет отбрасывается у следующего однозначного разделителя.

## Сообщения

| ID | Имя | Направление | Payload |
| ---: | --- | --- | --- |
| `01` | `Hello` | Host → ESP32 | Пустой |
| `02` | `DeviceInfo` | ESP32 → host | 16 байт информации об устройстве |
| `03` | `Ping` | Host → ESP32 | Произвольные байты для повтора |
| `04` | `Pong` | ESP32 → host | Точная копия payload `Ping` |
| `05` | `GetState` | Host → ESP32 | Пустой |
| `06` | `State` | ESP32 → host | 28 байт состояния |
| `10` | `SetStripConfig` | Host → ESP32 | 24 байта конфигурации ленты |
| `11` | `SetMode` | Host → ESP32 | Один байт режима |
| `12` | `SetBrightness` | Host → ESP32 | Один байт яркости |
| `13` | `SetEffect` | Host → ESP32 | 8 байт параметров эффекта |
| `14` | `SaveConfig` | Host → ESP32 | Пустой |
| `20` | `LedFrame` | Host → ESP32 | Кадр RGB8 |
| `70` | `Ack` | ESP32 → host | 4 байта подтверждения |
| `71` | `Error` | ESP32 → host | 4 байта ошибки |

Флаг заголовка `0x0001` запрашивает подтверждение. Флаг `0x0002` резервирует
запрос сохранения там, где команда его поддерживает. Остальные биты должны
быть нулевыми.

`ACK_REQUESTED` допустим только для изменяющих состояние команд:
`SetStripConfig`, `SetMode`, `SetBrightness` и `SetEffect`. Для `Hello`,
`Ping`, `GetState` и `LedFrame` флаги равны нулю: у первых трёх есть обычный
ответ, а высокочастотный видеопоток не должен ждать ACK на каждый кадр.

`SaveConfig` зарезервирован форматом, но текущая прошивка его не поддерживает
и отвечает `UnsupportedMessage`. Бит возможности persistent configuration в
`DeviceInfo` не выставляется.

## Жизненный цикл сессии

1. Host открывает вручную выбранный или ранее подтверждённый COM-порт с
   фиксированными параметрами.
2. После settle-паузы host отправляет `Hello` с новым sequence number и при
   необходимости повторяет тот же пакет на одном handle до общего deadline.
3. Устройство отвечает `DeviceInfo` с тем же sequence number.
4. Host проверяет версию протокола и наличие возможности RGB8 frames.
5. Host отправляет актуальные команды конфигурации с `ACK_REQUESTED`.
6. Только после подтверждения всех актуальных команд начинается передача
   `LedFrame`.
7. `GetState → State` используется для периодической телеметрии и проверки
   живости.

`Hello` обозначает начало новой host-сессии: ESP32 очищает ambient lease и
базовую последовательность кадров. Повтор с тем же sequence допустим только
во время начального handshake, чтобы пережить auto-reset ESP32 при открытии
USB-UART. После подключения `Hello` не служит keepalive.

Первое подключение требует ручного выбора USB-UART. После корректного
`DeviceInfo` desktop сохраняет только подтверждённую постоянную SetupAPI-
идентичность: VID/PID, Container ID и уникальный USB serial из device instance.
COM используется лишь как подсказка и может измениться. Automatic открывает
только точное совпадение этой идентичности; остальные COM-порты не зондируются.
Если драйвер не сообщает уникальный serial либо сообщает известную заглушку,
как у многих CH340-клонов, устройство остаётся доступно только вручную:
топологический Container ID сам по себе недостаточно надёжен. Bluetooth RFCOMM,
распознанный через QueryDosDevice или SetupAPI, запрещён в обоих режимах. Тайм-аут
открытия, handshake, ACK, I/O-ошибка или длительное отсутствие корректных
ответов приводят к безопасному закрытию и новой попытке подключения.
Если несколько клонов сообщают один и тот же правдоподобный serial, Windows
не позволяет доказательно различить их; для них пользователь должен сохранить
ручной режим.

## Политика очереди транспорта

Это правила desktop-транспорта поверх wire format:

- управляющие пакеты имеют приоритет над `LedFrame`;
- одновременно ожидается `Ack` только одной изменяющей состояние команды;
  следующая выбирается заново из актуального желаемого состояния, а `Off`
  имеет приоритет;
- одновременно хранится только один ещё не отправленный LED-кадр;
- новый кадр заменяет старый ожидающий кадр;
- изменение раскладки или выход из Ambilight очищает сохранённый кадр;
- до завершения handshake и синхронизации управляющих команд кадр не
  отправляется.

Desktop Duplication может не выдавать новый sample для полностью статичного
рабочего стола. В этом случае транспорт повторяет последние RGB-байты с новым
sequence number. Интервал keepalive выбирается не больше примерно трети
ambient timeout, чтобы lease на ESP32 оставалась активной.

## Полезные нагрузки

Все многобайтные целые числа далее используют little-endian. Каждый reserved
байт должен быть равен нулю.

### `DeviceInfo` — 16 байт

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 1 | Major-версия прошивки |
| 1 | 1 | Minor-версия прошивки |
| 2 | 1 | Patch-версия прошивки |
| 3 | 1 | Версия протокола |
| 4 | 2 | Максимальное поддерживаемое число LED |
| 6 | 2 | Текущее настроенное число LED |
| 8 | 4 | Биты возможностей |
| 12 | 4 | Uptime в миллисекундах по модулю 2³² |

Биты возможностей:

| Бит | Значение | Возможность |
| ---: | ---: | --- |
| 0 | `0x01` | Кадры RGB8 |
| 1 | `0x02` | Автономные эффекты |
| 2 | `0x04` | Постоянное хранение конфигурации |
| 3 | `0x08` | Ограничение тока |
| 4 | `0x10` | Ambient lease |

Текущая прошивка сообщает все перечисленные возможности, кроме постоянного
хранения.

### `SetStripConfig` — 24 байта

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 2 | Общее число LED, 1–300 |
| 2 | 2 | LED сверху |
| 4 | 2 | LED справа |
| 6 | 2 | LED снизу |
| 8 | 2 | LED слева |
| 10 | 2 | Циклическое смещение начала, меньше общего числа |
| 12 | 1 | Обратное направление: строго `0` или `1` |
| 13 | 1 | Порядок цветовых каналов |
| 14 | 1 | Потолок яркости контроллера, 0–255 |
| 15 | 1 | Reserved |
| 16 | 2 | Ограничение расчётного тока, мА: не меньше `3 × ledCount`, не больше 10000 |
| 18 | 2 | Тайм-аут ambient lease, мс, 100–60000 |
| 20 | 1 | Калибровка красного канала, 0–255 |
| 21 | 1 | Калибровка зелёного канала, 0–255 |
| 22 | 1 | Калибровка синего канала, 0–255 |
| 23 | 1 | Reserved |

Сумма четырёх сторон должна совпадать с общим числом LED. Значения порядка
каналов: `0` RGB, `1` RBG, `2` GRB, `3` GBR, `4` BRG, `5` BGR.
Калибровка каналов применяется прошивкой перед общим потолком яркости и
ограничением тока. Значение 255 оставляет канал без изменений, а 0 полностью
его подавляет. Поэтому одна настройка действует и на Ambilight, и на автономные
эффекты.

Смещение, направление и раскладка нужны для общей конфигурации, но сам
`LedFrame` desktop уже передаёт в окончательном физическом порядке. Прошивка
не применяет mapping второй раз.

### Режим, яркость и эффект

`SetMode` содержит один байт:

| Значение | Режим |
| ---: | --- |
| `0` | Off |
| `1` | Ambilight |
| `2` | Сплошной цвет |
| `3` | Автономный эффект |

`SetBrightness` — один байт от 0 до 255.

`SetEffect`:

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 1 | Эффект: `0` цвет, `1` дыхание, `2` волна, `3` радуга |
| 1 | 1 | Интенсивность, 0–255 |
| 2 | 1 | Красный канал |
| 3 | 1 | Зелёный канал |
| 4 | 1 | Синий канал |
| 5 | 1 | Reserved |
| 6 | 2 | Скорость в промилле, 10–10000 |

Отдельной команды fallback в v2 нет. ESP32 запоминает последний
не-Ambilight режим и его эффект. Desktop сначала программирует этот режим,
затем включает Ambilight. После истечения lease прошивка рендерит сохранённый
fallback, не ожидая host.

### `LedFrame`

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 2 | Число LED, 1–300 |
| 2 | 1 | Формат пикселя, сейчас `0` для RGB8 |
| 3 | 1 | Reserved |
| 4 | count × 3 | Байты RGB в окончательном порядке физической ленты |

Число LED должно совпадать с активной конфигурацией. Desktop уже применил
интерполяцию, смещение и направление. RGB передаётся без desktop-масштаба
яркости: потолок яркости и ограничение тока применяет ESP32.

Прошивка принимает только более новый frame sequence number. Если задача
вывода ещё не применила предыдущий ожидающий кадр, новый заменяет его и
увеличивает счётчик dropped frames.

### `State` — 28 байт

| Смещение | Размер | Поле |
| ---: | ---: | --- |
| 0 | 1 | Рабочий режим |
| 1 | 1 | Выбранный эффект |
| 2 | 1 | Эффективный потолок яркости |
| 3 | 1 | Флаги состояния |
| 4 | 2 | Число LED |
| 6 | 2 | Ограничение тока, мА |
| 8 | 4 | Sequence последнего принятого кадра |
| 12 | 4 | Sequence последнего применённого кадра |
| 16 | 4 | Число ошибок CRC |
| 20 | 4 | Число отброшенных кадров |
| 24 | 4 | Uptime в миллисекундах по модулю 2³² |

Флаги состояния: `0x01` — физический LED-выход присутствует, исправен и
активирован ненулевой яркостью в режиме, отличном от `Off`; `0x02` — ambient
lease активна; `0x04` — конфигурация изменена, но не сохранена. В безопасной
сборке без GPIO и во время восстановления RMT флаг `0x01` сброшен.

### `Ack` и `Error`

`Ack` содержит тип подтверждённого сообщения по смещению 0, status по
смещению 1 и два нулевых reserved-байта.

`Error` содержит 16-битный код ошибки, тип неудавшегося сообщения и
однобайтовый detail:

| Код | Значение |
| ---: | --- |
| `1` | Неподдерживаемая версия протокола |
| `2` | Неподдерживаемое сообщение |
| `3` | Некорректный payload |
| `4` | Недопустимое состояние |
| `5` | Устройство занято |
| `6` | Внутренняя ошибка |

Ответ повторяет sequence number запроса. Сравнение sequence number выполняется
по модулю 2³².

## Граница проверки

Формат заголовка, COBS, CRC-32C, все payload-кодеки, максимальный
300-пиксельный кадр и правила desktop-очереди проверяются host-тестами.

Фактическая устойчивость USB-UART при 2 Мбит/с, время handshake/ACK,
поведение при физическом отсоединении кабеля и совместная работа с реальным
UART0 ESP32 требуют проверки на устройстве. Документ фиксирует реализованный
контракт, но не заявляет завершённый сквозной аппаратный тракт.
