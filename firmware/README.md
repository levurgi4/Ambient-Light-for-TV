# Прошивка Ambilight

Прошивка на C++20 и ESP-IDF 6.0.2 для ESP32-WROOM-32D. Она принимает
бинарные кадры по UART, рисует автономные эффекты и умеет физически выводить
до 300 пикселей WS2815 через периферию RMT.

## Безопасность по умолчанию

- После запуска выбран режим `off`.
- Текущий `sdkconfig.defaults` выбирает GPIO18 только для уже проверенной
  разводки прототипа. Для новой платы установите
  `CONFIG_AMBILIGHT_LED_DATA_GPIO=-1`: строгий `NoopLedOutput` не настраивает
  и не переключает ни один GPIO ленты.
- Физический RMT-выход появляется только в сборке, где GPIO выбран явно.
  Перед созданием RMT-канала дополнительно проверяются конфигурация ленты и
  консервативный список допустимых выводов ESP32-WROOM-32D. После успешного
  запуска первый RMT-кадр гасит ранее защёлкнутые цвета ленты.
- Яркость по умолчанию ограничена значением 128/255, программный лимит тока —
  5000 мА. Консервативная оценка суммирует все три канала как 12 мА каждый и
  добавляет 3 мА покоя на пиксель; коэффициенты всё равно нужно откалибровать
  измерением именно вашей ленты. Конфигурация отклоняется, если лимит ниже
  `3 мА × число пикселей`: собственное потребление электроники ленты
  программно не ограничивается, поэтому обещать такой бюджет было бы неверно.
- Кадр Ambilight имеет lease 1000 мс. После потери кадров прошивка возвращается
  к последнему автономному режиму; начальный резервный режим — `off`.

Для текущего короткого соединения подтверждены общая земля и прямой сигнал
GPIO18 → 330–470 Ом → DI. Буфер уровня 3,3 → 5 В не потребовался; его следует
добавлять только при фактической нестабильности, предусмотрев безопасное `OE`,
развязку питания и внешний pull-down. Подключение резервной линии `BI`
выполняется по физической схеме; прошивка управляет только `DIN`.

Не питайте плату одновременно от USB и понижающего преобразователя, пока схема
питания конкретной DevKit-платы не подтверждает, что это безопасно.

Согласованная топология питания, буфера и ленты, а также порядок первого
включения находятся в [физической схеме](../docs/hardware-wiring.md).

## Как включить физический выход

Откройте окружение `IDF_v6.0.2_Powershell`, затем:

```powershell
cd C:\Dev\Ambient-Light-for-TV\firmware
idf.py menuconfig
```

GPIO и профиль импульсов находятся в меню `Ambilight hardware`. Значение GPIO
`-1` отключает физический выход. Такая сборка остаётся совместимой с протоколом
RGB-кадров для безопасной отладки, но не поднимает флаг активного выхода и не
увеличивает `lastAppliedSequence`. Разрешены только GPIO:

```text
16, 17, 18, 19, 21, 22, 23, 25, 26, 27, 32, 33
```

Из списка намеренно исключены UART0 (GPIO1/3), выводы flash, входы без
возможности output и загрузочные strapping-пины. GPIO18 подтверждён только для
текущей DevKit-платы; другой разрешённый GPIO может быть занят на другой плате.
Протокол устройства не содержит GPIO: это параметр сборки, а не настройка с ПК.

После выбора проверенного вывода:

```powershell
idf.py build
```

По умолчанию выбран профиль `Classic WS2815 / early WS2815B`, сохраняющий
исходные тайминги:

- `0`: 250 нс HIGH + 1000 нс LOW;
- `1`: 1000 нс HIGH + 250 нс LOW;
- reset/latch: 300 мкс LOW.

Для ленты с контроллером из обновлённой спецификации `WS2815B-V1` выберите
профиль `Revised WS2815B-V1`: в нём бит `1` имеет 750 нс HIGH + 625 нс LOW.
Эти варианты несовместимы по длительности LOW, поэтому профиль нужно сверить
с маркировкой/спецификацией фактической ленты или осциллографом. Для ленты,
продаваемой без указания ревизии просто как WS2815, безопаснее оставить
совместимый с исходной прошивкой профиль Classic до аппаратной проверки.

Передаваемые с ПК кадры уже находятся в окончательном физическом порядке
индексов. Прошивка применяет только выбранный порядок цветовых каналов
(`RGB`, `RBG`, `GRB`, `GBR`, `BRG` или `BGR`) и **не** повторяет `start_offset`
или `reversed` для Ambilight-кадров. Автономные пространственные эффекты
`wave` и `rainbow` используют эти параметры, чтобы направление и начало
совпадали с настройкой периметра.

При ошибке RMT прошивка оставляет `lastAppliedSequence` на последнем физически
показанном кадре, снимает флаг активного выхода и повторяет полную
инициализацию не чаще одного раза в секунду. Непоказанный кадр остаётся
ожидающим: кадр, пришедший во время RMT-передачи, становится отдельным queued
кадром и не вытесняет уже in-flight кадр. При ошибке in-flight кадр возвращается
в очередь, если более новый кадр ещё не занял её; иначе только неудавшийся
in-flight кадр считается dropped. Queued кадр считается dropped при замене
следующим queued кадром, изменении конфигурации/начале новой host-сессии или
истечении lease. Точный повтор уже применённого `SetStripConfig` считается
ACK-retry и ничего не инвалидирует.

## Сборка и прошивка

```powershell
cd C:\Dev\Ambient-Light-for-TV\firmware
idf.py set-target esp32
idf.py build
```

Когда станут известны COM-порт и USB-UART-драйвер платы:

```powershell
idf.py -p COMx flash
```

Не запускайте обычный текстовый `idf.py monitor` одновременно с приложением:
после загрузки UART0 занят бинарными COBS-пакетами на скорости 2 000 000 бод.
ROM ESP32 всё ещё может кратко отправить загрузочный текст на 115200 бод.
После переключения скорости прошивка отправляет нулевой разделитель, чтобы
декодер ПК синхронизировался до первого ответа.

После открытия COM-порта приложение отключает DTR/RTS и дальше намеренно их
не импульсирует. На распространённых DevKit-платах эти сигналы подключены к
EN/GPIO0 и могут перезагрузить ESP32 или перевести её в загрузчик, поэтому
момент открытия нужно проверить с драйвером конкретного USB-UART.

## Устройство прошивки

- `UartTransport`: UART0 RX на ядре 0. События драйвера передают декодеру ровно
  уже полученные байты, поэтому полный LED-кадр не ждёт 20-миллисекундный
  таймаут или начало следующего кадра.
- `ProtocolDispatcher`: общий COBS + CRC32C-декодер из `shared/protocol` и
  обработчики hello, ping, state/config, mode/effect и LED-frame.
- `DeviceState`: защищённая блокировкой конфигурация и один заменяемый кадр
  Ambilight. Всегда побеждает самый свежий кадр; растущей очереди нет.
- `EffectsEngine`: рендер на ядре 1. Дробный график 16/17 мс даёт ровно 60 Гц
  без накопления дрейфа; просроченные слоты отбрасываются без burst-догоняния.
- `RmtLedOutput`: синхронная передача WS2815, порядок каналов и проверка
  размера кадра. Одинаковый кадр ограничивается по частоте, но раз в секунду
  защёлкивается снова, чтобы восстановиться после отдельного перезапуска
  питания ленты или помехи. Перед уменьшением длины backend гасит прежний
  полный диапазон, чтобы светодиоды за новой границей не оставались
  защёлкнутыми. По умолчанию backend не создаётся.
- `NoopLedOutput`: полностью безопасный backend для стандартной сборки.

LED-кадры не подтверждаются ACK-пакетами. `GET_STATE` сообщает последние
полученный и применённый sequence, ошибки CRC и отброшенные/заменённые кадры.
Изменяющие состояние команды получают ACK при установленном
`PacketFlagAckRequested`; некорректные запросы получают error-пакет.

## Host-тесты чистой логики

Порядок каналов, валидация GPIO/конфигурации и дробный 60-герцовый график не
зависят от ESP-IDF и проверяются обычным компилятором:

```powershell
cmake -S firmware/tests -B out/build/firmware-host-tests `
  -G "Visual Studio 17 2022" -A x64
cmake --build out/build/firmware-host-tests --config Debug
ctest --test-dir out/build/firmware-host-tests -C Debug --output-on-failure
```

## Что останется проверить на железе

GPIO18, прямое короткое соединение через резистор, порядок `RGB`, все 300 LED
и UART 2 Мбит/с уже подтверждены на собранном прототипе. Далее нужно:

1. Провести длительную проверку нагрева и стабильности при разных сценах.
2. При появлении помех проверить осциллографом форму сигнала и только тогда
   добавить согласованный level shifter с безопасным управлением `OE`.
3. Измерить реальное потребление и откалибровать модель ограничения тока.
4. Измерить частоту обновления ленты и полную задержку на 4K/60 Гц.
5. Добавить NVS-персистентность. Пока она не заявлена в `DeviceInfo`, а запрос
   сохранения возвращает `UnsupportedMessage`.
